# ستون فقرات مدل مبدأ

قاعدهٔ حاکم: **هر نوع Relation فقط وقتی مجاز است که یک موتور آن را بخواند.** مفهومی که هیچ موتوری نخواند، ذخیره نمی‌شود.

| مفهوم | تعریف یک‌خطی | چه چیزی نیست | کدام موتور می‌خواند |
| --- | --- | --- | --- |
| **Workspace** | مرز حقیقت: هر کسب‌وکار/مشتری یک Workspace؛ هیچ داده‌ای از مرز رد نمی‌شود. | پوشه یا پروژهٔ نمایشی نیست؛ پلن و سقف‌ها به آن بسته‌اند. | همهٔ موتورها (scope = userId + workspaceId) |
| **Node** | دامنهٔ معنا در درخت (کسب‌وکار، مخاطب، پیشنهاد…)؛ زیرگره‌ها حقیقت را به ارث می‌برند. | دسته‌بندی سلیقه‌ای نیست؛ گرهٔ سیستمی فقط تغییر نام می‌گیرد. **ترتیب نیست:** هم‌سطح‌ها تقدمی ندارند. | `nodeTree`، `contextEngine` (ارث‌بری)، `aiContext` |
| **Context Object** | واحد حقیقت؛ فقط `Fact` / `Decision` / `Constraint`. دو قید دامنه دارد: `reach` (`global` \| `position`؛ پیش‌فرض Constraint = `global`، Fact/Decision = `position`) و `validUntil` (اختیاری). | خروجی، یادداشت یا پاسخ مدل نیست. | Gap، Readiness، تناقض، `contextPack`، `impactEngine` |
| **Status** | وضعیت اعتبار: Confirmed، Proposed، Needs Review (علامت دستی کاربر)، Superseded، Archived. فقط Confirmed «واقعیت» است. | منشأ را نمی‌گوید. «نیاز به بازبینی» به‌خاطر وابستگی، وضعیت نیست؛ مشتق است (Staleness). | `contextEngine`، `context.ts` (Proposed هرگز واقعیت به مدل داده نمی‌شود) |
| **Provenance** | منشأ ثبت: Onboarding، User Input، AI Suggested، Imported، Asset Derived. | اعتبار نمی‌دهد؛ AI Suggested بدون تأیید واقعیت نیست. | صندوق پیشنهادها، `changeFeed` |
| **Relation** | یال بین Objectها در سه خانواده (زیر). | برچسب تزئینی نیست. | زیر هر خانواده |
| ↳ ساختاری `belongs_to` | Object به Node تعلق دارد (`nodeId`، نه ردیف جدا). | — | `contextEngine`، `aiContext` |
| ↳ وابستگی `depends_on` | این تصمیم روی آن تصمیم سوار است. (دستی فقط همین و `supersedes` با تأیید صریح؛ `belongs_to` و `derived_from` ردیف نمی‌شوند.) | وابستگی داده‌ای/زمانی بین خروجی‌ها نیست (آن در Spec است). | `decisionGraph` (ترتیب، همزمانی، نیاز به بازبینی)، `impactEngine` |
| ↳ استثنا `overrides` | Object گرهٔ **فرزند** → Object گرهٔ **والد/اجداد**: آن Object فقط برای همان گره و زیرشاخه‌اش از «فهرست مؤثر» خارج می‌شود (والد و هم‌سطح‌ها دست‌نخورده). فقط با دلیل (در Change)؛ معتبر تا وقتی مورد استثناکننده زنده و منقضی‌نشده است. | حذف یا ویرایش مورد والد نیست؛ اگر خودِ والد اشتباه است باید جایگزینش کرد. بین هم‌سطح‌ها یا از والد به فرزند مجاز نیست. | `effectiveContext` (و هرچه از آن می‌خواند: گاردریل، بستهٔ Context، گفتگوی گره) |
| ↳ تبار `derived_from` / `supersedes` | `supersedes`: نسخهٔ تازه جای قدیمی. `derived_from`: Asset از Objectهای با نسخهٔ دقیق (`usedContext`). | `derived_from` ردیف جدول نیست؛ همان `usedContext` است. | `impactEngine`، `contradictionCandidates` |
| **Source** | شاهد: آنچه Object از آن آمد (کدام AI/فایل/یادداشت، چه وقت، نقل دقیق). | دلیل تغییر نیست. | صندوق پیشنهادها، `memory import` |
| **Note / Material** | متن خامِ مستقل روی یک Node؛ می‌تواند هیچ Thought یا چند Thought بسازد. نشانگرهای فعلی برای ورود/همگام‌سازی Thought به‌کار می‌روند، اما متن Note و هویت Thought یکی نیستند. | Knowledge یا Truth نیست؛ ویرایش یا حذف Note، متن Thought را بازنویسی یا حذف نمی‌کند. هیچ Note خامی به مدل نمی‌رود. | `notes`؛ ورودی Thought |
| **Slot** | جایگاه نام‌دار که Spec می‌خواهد (`slotKey`)؛ Object آن را پر می‌کند. | عنوان نیست؛ عنوان فقط برای دادهٔ قدیمی. | `contextEngine.fillsItem` |
| **فهرست مؤثر** | آنچه در یک گره **اثر دارد**: Objectهای همان گره (`own`) و گره‌های بالاتر (`inherited`)، به‌علاوهٔ قیدهای `global`؛ منهای استثناها (`overridden`) و منقضی‌ها (`expired`). یک Object در گرهٔ N به N و زیرشاخه‌هایش اثر دارد، نه به والد و نه به هم‌سطح. | ذخیره نمی‌شود؛ هر بار از Objectها، درخت و `overrides` محاسبه می‌شود. | `effectiveContext` ← گاردریل هر خروجی، گفتگوی گره، بستهٔ Context و اعتبارسنج |
| **Gap / Readiness / تناقض** | مشتق از Objectها و Spec؛ هر بار محاسبه می‌شوند. کاندید تناقض سه سیگنال ساختاری هم دارد: همان slot، `depends_on` (`linked`) و هم‌گره‌هم‌نوعِ با متن نزدیک. | ذخیره نمی‌شوند (جز حکم مدل برای جفت تناقض به‌عنوان کش). قضاوت فقط پس از تغییر Objectِ یک جفت یا با دکمه، نه با باز کردن فضا. | `contextEngine`، `contradictionCandidates` |
| **Workstream** | جریان کار: هدف + خروجی‌های وابسته. **Spec فقط تعریف داخلی** آن است. جریان‌های آماده یک «کتابخانه»اند؛ هر فضا فقط آنچه برداشته (`Workspace.enabledSpecIds`؛ نبودنِ فیلد = همهٔ پیش‌فرض‌ها) و جریان‌های خودش را دارد. | داده یا حقیقت نیست. | `specGraph`، pipeline |
| **Asset** | خروجی ساخته‌شده (Markdown) با Lineage. | از نوع Context نیست (`ContextType` فقط Fact/Decision/Constraint)؛ «پیشنهاد دانش از این خروجی» از مسیر استخراج Proposed با نقل منبع می‌سازد و کاربر تأیید می‌کند. | `impactEngine` |
| **Lineage** | فهرست دقیق `{id, version}` Objectهای تزریق‌شده هنگام ساخت Asset. | — | `impactEngine` |
| **Impact** | اثر یک تغییر: کدام Assetها (و وابسته‌ها) از Objectِ عوض‌شده ساخته شده‌اند. | — | `impactEngine` |
| **Staleness** | «قدیمی» (دارایی) و «نیاز به بازبینی» (تصمیم وابسته): **مشتق**، نه ذخیره‌شده. «بدون تغییر بپذیر» فقط یک Change از نوع `review_accepted` می‌نویسد. | — | `impactEngine` (دلیل `dependency_changed`)، `decisionGraph.needsReview` |
| **ساختار حقیقت** | درخت Node و دانش هر بخش؛ depth از زنجیرهٔ والدها مشتق می‌شود. | هم‌سطحی یا nesting به‌تنهایی dependency/تقدم نیست. | `nodeTree`, `ContextTreeDocView` |
| **نمای کلی حقیقت** | ردیف = بخش؛ یال و جایگاه ستون = فقط رابطهٔ صریح `depends_on`. | چیدمان یا موقعیت رابطه نمی‌سازد؛ نبود یال در نما، نبود ترتیب را القا نمی‌کند. | `swimlane`, `decisionGraph` |
| **دور این مورد** | نمای زمینه‌ای dependency و اثر برای یک دانش انتخاب‌شده؛ منشأ و Assetهای وابسته از دادهٔ موجود خوانده می‌شوند. | مقصد/گراف مستقل نیست؛ از نمای کلی باز می‌شود. | `lineage`, `influence`, `provenance` |
| **بوم فکر** | فضای آزاد Thought و Material خام؛ جایگاه نمایشی است و به‌خودی‌خود معنای رابطه ندارد. | Truth یا dependency نیست. | `canvasScene` (`free`) |
| **Board (مدل قدیمی)** | منطق/دادهٔ rank تاریخی هنوز در `canvasModel`/`canvas_view_items` موجود است، اما در رابط فعلی عرضه نمی‌شود. | چیدمان فعال Thinking نیست. | کتابخانهٔ داخلی؛ پارک‌شده برای پاک‌سازی مستقل |
| **Thought** | واحد قابل اقدامِ فکر با شناسهٔ ذخیره‌شدهٔ مستقل از متن؛ منشأ Material و وضعیت open/resolved اختیاری/مستقل‌اند. | Note یا Knowledge/Truth نیست؛ به‌طور ضمنی وارد مدل نمی‌شود. | `thoughts`, `thinkingMarkers`, `thinkingSpace` |
| **فرض** | یک Fact با `assumption` و `review_by`: «این‌طور فکر می‌کنیم». حتی Confirmed هم **دانش تأییدشده نیست**: در بستهٔ Context و prompt در بخش جدای «فرض‌های فعال، تأییدنشده» با دستور صریح می‌رود و readiness آن را دانش تأییدشده حساب نمی‌کند. | واقعیت نیست؛ فقط با «واقعیت شد» (Change با دلیل) دانش می‌شود. | `assumptions` ← بسته، prompt، «این هفته»، «خانه» |
| **رکورد تصمیم** | اختیاری روی یک Decision (ستون JSON): سؤال، گزینه‌های بررسی‌شده + دلیل ردشدن هرکدام، انتظار، تاریخ بازبینی. «گزینه‌های ردشده» به بسته و prompt می‌رود تا AI دوباره پیشنهادشان نکند. در بازبینی هفتگی، تصمیمِ سررسیدشده می‌پرسد «نتیجه چه شد؟» ← Change از نوع `outcome_noted` (بدون KPI). | قاعده یا گاردریل نیست؛ فقط حافظهٔ «چرا این را انتخاب کردیم». | `assumptions.rejectedOptions/decisionsDue` |
| **بُعد (facet)** | یک محور آزاد روی Object: آرایه‌ای از نام‌ها («مخاطب سازمانی»، «فصل پاییز») که از میان درخت می‌گذرد. فقط یک محور؛ سلسله‌مراتب دوم نیست. | دامنه و وابستگی را عوض نمی‌کند و تقدم نمی‌سازد. | فیلتر جدول، رنگ‌بندی/خطوط شنای نقشه و بوم، انتخاب در بسته |
| **بستهٔ ذخیره‌شده** | یک انتخاب نام‌دار (گره‌ها، بُعدها، وضعیت‌های اضافه، شمول فرض‌ها) + دستور کوتاه برای AI (`saved_packs`). هر بار از **فهرست مؤثر** بخش‌های انتخاب‌شده (با یا بی «با زیربخش‌ها») حل می‌شود — قاعده در بخش «دامنهٔ بسته و درخواست برای AI» پایین. فقط Confirmed واقعیت است؛ فرض‌ها و «گزینه‌های ردشده» جدا با دستور صریح؛ هرگز نمونه. | نسخهٔ ثابت یا خروجی نیست؛ هر بار از دانش فعلی ساخته می‌شود. | `contextPack` ← UI (کپی، نسخهٔ چاپی) و واردکردن پاسخ |
| **نمونه (sample)** | Objectی که با اسکلت شروع یا قالب آمده؛ خاکستری با برچسب «نمونه». **فیلتر مرکزی:** `repo.listObjects` / `getObject` / شمارش پلن هرگز نمونه را نمی‌دهند؛ فقط `state.samples` برای نمایش. ویرایش یک نمونه آن را مال کاربر می‌کند (آن‌وقت دانش است). | دانش نیست؛ به هیچ AI و هیچ موتوری (تزریق، بسته، Gap، Readiness، تناقض، اعتبارسنج، اثر) نمی‌رسد. | هیچ موتوری — فقط نمایش |
| **قالب** | گره (با زیرشاخه و دانش تأییدشده‌اش) یا جریان کار خود کاربر، در سطح **کاربر** (`templates`)؛ در هر فضا برمی‌گردد: گره‌ها واقعی، دانش‌ها نمونه. | قالب دانش نیست. | `templates` ← مسیر apply |
| **شاخص (Metric) و اندازه‌گیری (Measurement)** | نتیجهٔ واقعی که کاربر دنبال می‌کند: شاخص = نام، واحد، جهت (بالاتر / پایین‌تر بهتر)، هدفِ اختیاری؛ اندازه‌گیری = مقدار، روز، یادداشت، منبع (`manual`/`csv`/`mcp`/`demo`)، وضعیت (`Confirmed`/`Proposed`)، ارجاع اختیاری به تصمیم. هر نوشتن یک Change با `object_id = metric:<id>` می‌گذارد (از فهرست تغییرهای Context جداست). | **Object نیست و هرگز Fact نمی‌شود**؛ دانشِ تأییدشده نیست؛ به Gap/Readiness/تناقض/اعتبارسنج وارد نمی‌شود. اندازه‌گیری‌های legacy با منبع `mcp` **همیشه** `Proposed` می‌مانند تا کاربر تأییدشان کند؛ این منبع دیگر ورودی فعال ندارد. | `metrics.ts`، بستهٔ Context (بخش جدا) |
| **انتظار (expectation)** | روی یک Decision (داخل `record`، بدون ستون تازه): `{ metricId, direction, targetValue?, by }`. «انتظار در برابر نتیجه» فقط حساب است: آخرین عدد تا روز تصمیم، آخرین عدد تا `by`، هدف. داوری «به انتظار رسید / نیمه / نرسید» را **کاربر** می‌نویسد (Change از نوع `outcome_noted` با `after.verdict`، `metricId` و عددی که با آن خوانده شد)؛ ✓ فقط خوانش حسابی و پیش‌انتخاب است. | ادعای علّی نیست: واژه‌ها «پس از» و «انتظار در برابر نتیجه»‌اند، هرگز «اثر» یا «علت» (تست روی متن‌های UI و منبع کامپوننت‌ها این را اجبار می‌کند). مدل یادگیرنده نیست. | `metrics.ts`، «این هفته»، خانه |
| **درخواست برای AI** | یک «نوع کار» (سؤال، ممیزی، پیش‌نویس، تصمیم، بازبینی تغییر، آزاد) + یک خط + دامنه (گره؛ پیش‌فرض کل درخت) که `aiRequest` به یک متن اصولی تبدیل می‌کند: اول اسناد برچسب‌دار (`id@version` و منشأ؛ فرض‌ها جدا؛ قیدها؛ تصمیم‌ها و گزینه‌های ردشده؛ شاخص‌ها؛ برای بازبینی: قبل/بعد؛ برای ممیزی: شکاف‌ها)، بعد قواعد همان نوع، بعد درخواست، بعد قالب پاسخ قابل‌ورود. **انتخاب:** قیدهای مؤثر و تصمیم‌های `reach: global` همیشه؛ بقیه با BM25 روی درخواست + برچسب گره + بُعدها تا بودجهٔ توکن؛ هر چه نیامد با دلیل (دامنه، منقضی، استثنا، تأییدنشده، نمونه، بودجه، بی‌ربط) فهرست می‌شود و کاربر می‌تواند دستی اضافه کند (جز نمونه و تأییدنشده). درخواست ذخیره‌شده همان ردیف `saved_packs` است با `kind` و `template`؛ هر بار با دانش روز ساخته می‌شود. | هیچ AI‌ای صدا زده نمی‌شود و هیچ پاسخی ساخته نمی‌شود؛ Proposed، Needs Review و نمونه هرگز واقعیت نمی‌آیند؛ `reason` تغییرها هرگز نمی‌آید. | `aiRequest`، مسیر `/ai-requests`، `saved_packs` |
| **نمای سند (تب + outline)** | همان Markdown خطیِ درخت، ولی بخش‌های سطح اول درخت «تب»اند (`docTabs`: با یک ریشه، فرزندان ریشه؛ دانش خود ریشه در تب «کلیات» فقط اگر باشد). هر تب فهرستی (outline) از سرتیترهای خودش دارد با **نشانی ثابت** (`#n-<شناسهٔ گره>` / `#o-<شناسهٔ Object>`؛ از شناسه می‌آید نه از متن، پس با تغییر عنوان نمی‌شکند) و «اکنون کجایی» (scroll-spy). نشانی یک Object تب خودش را باز می‌کند. روی موبایل outline منوی «فهرست» است. گزینهٔ «با ارجاع‌ها» فقط دو خط تخت (`وابسته به: …` و `برگرفته از: …`) زیر هر Object می‌افزاید. | ساختار تو‌در‌تو، جدول یا سطح سرتیتر تازه به md اضافه نمی‌کند؛ دانش یا رابطه‌ای نمی‌سازد. | `contextMarkdown` (`contextDoc`، `docTabs`، `tabOfAnchor`) |
| **مسیر نسخه‌ها** | نمایش تاریخچهٔ یک Object: ویرایش‌های پیش‌نویس (نسخه‌هایی که وقتی Object تأیید نبود ساخته شدند؛ ثبت اولیه هم یکی است) در یک ردیف بستهٔ «N پیش‌نویس» می‌آیند و تأیید یک **نقطهٔ عطف** است («تأیید شد در نسخهٔ N»)؛ ویرایش Objectِ تأییدشده خودش نقطهٔ عطف («ویرایش تأییدشده → نسخهٔ N») با دلیل است. «آخرین تأیید: نسخهٔ N» نشان روی Object است. **شمارندهٔ نسخه همان است** (هر ویرایش محتوا +۱: ردپای Replay و `impactEngine`)؛ فقط نمایش گروه می‌شود. «دلیل» اختیاری فقط برای ویرایش دانش تأییدشده است (در `Change.reason`) و برای پیش‌نویس ثبت نمی‌شود (سرور نمی‌پذیرد). اثر ویرایش پیش‌نویس فقط روی چیزهایی است که همان نسخه را مصرف کرده‌اند: Proposed هرگز به مدل نمی‌رود، پس هیچ دارایی‌ای با آن «قدیمی» نمی‌شود (تست صریح در `impactEngine.test.ts`). | نسخهٔ تازه یا وضعیت تازه نمی‌سازد؛ فقط Changeها را می‌خواند. | `versionHistory` (از `context_changes`) |
| **جستجوی سراسری (Ctrl/⌘+K)** | یک جعبهٔ «پیدا کن و انجام بده»: کلیدواژه روی Objectها، گره‌ها، دارایی‌ها و یادداشت‌ها، با `normalizeFa` (ي/ك، ZWNJ، همزه، رقم) و BM25 (همان فرمول `retrieval.ts`)؛ آخرین کلمه پیشوند است (با چند حرف پیدا می‌شود). نتیجه‌ها گروه‌بندی می‌شوند؛ فرمان‌ها («ثبت دانش»، «درخواست برای AI»، «رفتن به …») بالا؛ گروه‌ها بر پایهٔ بهترین نتیجه مرتب می‌شوند تا چیزی که نامش را نوشتی ردیف اول باشد. کیبورد (↑↓ Enter Esc، `combobox`/`listbox`/`aria-activedescendant`)، RTL، روی موبایل دکمهٔ جستجوی سربرگ. | **یادداشت فقط برای نمایش جستجو می‌شود** و به هیچ AI‌ای نمی‌رود (قاعدهٔ یادداشت)؛ نمونه (sample)، بایگانی و جایگزین‌شده جستجو نمی‌شوند؛ چیزی نمی‌سازد یا نمی‌نویسد. | `globalSearch` (`buildSearchIndex`، `searchIndex`) |
| **ارجاع `@`** | در متن Object و یادداشت، `@` نام Objectها را پیشنهاد می‌دهد و `@«عنوان»` می‌نویسد. هنگام ذخیرهٔ یک Object، اگر متن به Objectِ دیگری اشاره می‌کند، چیپ «این متن به X اشاره می‌کند؛ رابطهٔ وابسته‌به بسازم؟» می‌آید؛ فقط با «بساز» و ذخیره، همان مسیر وابستگی (`setDependencies`) رابطه و **یک Change** می‌نویسد؛ «نه» برای همان جفت یادآوری می‌شود. عنوان تکراری = مبهم، هرگز حدس زده نمی‌شود. | هیچ رابطهٔ خودکار نمی‌سازد؛ یادداشت رابطه نمی‌گیرد (رابطه بین Objectهاست)؛ فقط به Objectِ تأییدشده/فعال پیشنهاد می‌دهد، نه Proposed، آرشیو یا جایگزین‌شده. | `mentions` (`extractMentions`، `suggestLinks`) |
| **خانه (سه کار) و سطح‌بندی** | «الان چه کاری ارزش دارد؟»: `homeActions` از خروجی موتورهای موجود حداکثر سه کار رتبه می‌دهد (خروجی به‌روز نیست — اخیراً ساخته‌شده بالاتر — › تناقض › دانشی که به‌خاطر تغییر نیاز به نگاه دارد › تصمیم آماده › پیشنهادهای منتظر › بازبینی هفتگی › موعد رسیده)، از هر نوع یکی؛ هر کدام یک جمله و یک دکمه. بقیه زیر «همه (N)». `visibleFeatures` تصمیم می‌گیرد کدام امکان سطح ۲ دیده شود (بازبینی هفتگی: تغییری در ۷ روز؛ تصمیم‌های منتظر: وابستگی؛ تناقض؛ شاخص‌ها؛ بسته‌ها؛ پیشنهادها). جدول زیر «⋯»؛ رادار شکاف و «مربی دانش» به‌صورت ورودی جدا از دید رفتند (مربی در شروع سریع و گفتگوی گره می‌ماند). | هیچ امکانی حذف نشده؛ فقط جابه‌جا یا پنهان (در «بیشتر» و جستجو پیدا می‌شود). موتور تازه‌ای نیست. | `homeActions`، `visibleFeatures` |
| **حدس نوع و عنوان** | در «ثبت دانش» کاربر فقط متن می‌نویسد؛ `guessType` («هرگز/نباید/نداریم» ← خط قرمز، «تصمیم گرفتیم/انتخاب کردیم» ← تصمیم، وگرنه واقعیت) و `guessTitle` (جملهٔ اول) پیش‌فرض می‌دهند و کاربر عوضشان می‌کند. وضعیت «تأییدشده» و منبع «ورودی کاربر» پرسیده نمی‌شوند. | حدس فقط پیش‌فرض است؛ چیزی را بی‌اطلاع کاربر قطعی نمی‌کند. | `knowledgeGuess` |
| **شمارندهٔ استفاده** | جدول `usage_events` (کلید امکان، شمار، آخرین زمان) فقط در همین نصب؛ کلید حتماً از فهرست `FEATURES` است (هر چیز دیگر رد می‌شود)، پس هیچ متن یا دادهٔ کاربر ذخیره نمی‌شود. فقط مدیر (`MABDA_ADMIN`) در منوی حساب «استفاده از امکانات» را می‌بیند: امکان سطح ۱ که کسی باز نمی‌کند مهم‌ترین یافته است. | داده‌ای از کاربر نیست؛ به هیچ AI یا بیرون نمی‌رود. | `usage` (`FEATURES`، `summarizeUsage`) |
| **سؤال بدون نحو** | خطی از یادداشت که با «؟» یا «?» تمام شود خودکار «سؤال» است (`isQuestionLine`؛ نشانگر صریح بر آن مقدم است)؛ منوی «علامت بزن» روی هر خط، نشانگر را با `markLine` می‌نویسد (برگشت‌پذیر؛ فقط همان خط عوض می‌شود). هیچ‌جای UI یادگیری براکت لازم نیست. | یادداشت و موردهای فکری هرگز به AI نمی‌روند (تست `aiContext`)؛ تبدیل همیشه «پیشنهادی». | `thinkingMarkers` (`isQuestionLine`، `markLine`، `displayLine`)، `NoteLines` |
| **مثال برای خط قرمز** | تا سه مثال «درست/نادرست» (ستون JSON `examples`، migration ۱۷) روی Constraint و Decisionِ همه‌جا؛ در «بیشتر» با «افزودن مثال». کنار همان قید در درخواست برای AI، بستهٔ Context، گفتگو و پرسش اعتبارسنج می‌آید؛ ویرایش آن نسخهٔ تازه می‌سازد (خروجی‌ها قدیمی می‌شوند). | نمونه‌ها (sample) هرگز؛ فقط متن است و وضعیت یا نسخهٔ جدا ندارد. | `redlineExamples` (`cleanExamples`، `examplesOf`، `guardrailText`) |
| **رابطه هنگام ثبت** | «روی چه اثر دارد؟» همان `depends_on` در جهت مخالف است (A روی B اثر دارد = B به A تکیه دارد)؛ هر دو جهت در «بیشتر» با جست‌وجو. `affectPlan` فقط مجموعهٔ وابستگی‌های تازهٔ اشیایی را می‌نویسد که تغییر می‌کنند. | نوع رابطهٔ تازه نیست؛ تقدم هنوز فقط از `depends_on`. | `relationPlan` (`affectPlan`، `affectedBy`، `restsOn`)، `RelationPicker` |
| **نسخه‌های یک دانش** | `versionTexts` متن هر نسخه را از رکوردهای تغییر بازمی‌سازد (رکورد «ساخته شد» متن ندارد؛ متن نسخهٔ اول از before اولین ویرایش می‌آید). برای «مقایسهٔ دو نسخه» و تفاوت «از زمان ساخت خروجی». | فقط خواندن؛ چیزی نمی‌نویسد. | `versionHistory` (`versionTexts`)، `textDiff` (`diffSummary`) |
| **Change** | رکورد افزوده‌شونده در همان تراکنش هر تغییر: object، نسخه از/به، kind، actor (+برچسب)، reason، فقط فیلدهای تغییرکرده (`context_changes`). | متن Object نیست؛ `reason` هرگز به مدل تزریق نمی‌شود. برچسب‌های actor قدیمی برای نمایش منشأ تاریخی حفظ می‌شوند. | `decisionGraph.needsReview`، `impactEngine` |
| **AI** | اجرا، نه اعتبار: پیشنهاد می‌دهد، قضاوت بسته می‌کند؛ تأیید همیشه با کاربر. | منبع حقیقت نیست. | router، pipeline، decision layer |

## ساختار تفکری داخل هر گره
بدون بخش جداگانه: صفحهٔ هر گره سه بخش دارد — **وضعیت فعلی** (Confirmed و لینک «آنچه اینجا اثر دارد»)، **در حال فکر** (پیشنهادی‌ها، فرض‌ها، موارد فکری و یادداشت‌ها) و **منابع** (فایل‌ها و ورودی‌ها). سؤال‌ها و تصمیم‌های بازِ همهٔ گره‌ها در «خانه» جمع می‌شوند. اقدام‌ها: «ببر بالاتر» (انتقال به گرهٔ والد یا همه‌جا، با دلیل در Change) و «تبدیل به گره» برای یادداشتی با دو تیتر `##` یا بیشتر (یک Change `node_from_note` به‌ازای هر گره با شناسهٔ `node:<id>`؛ متن اصلی می‌ماند). `outcome_noted` و `node_from_note` محتوا را عوض نمی‌کنند: نه نسخه می‌سازند، نه چیزی را «قدیمی» می‌کنند.

## قرارداد مفهومی Thinking (P1)

این قرارداد مرز مدل را تثبیت می‌کند؛ در P1 هیچ جدول، مهاجرت، موتور یا UI تازه‌ای ساخته نمی‌شود. وضعیت فعلی خطوط یادداشت، پیاده‌سازی موقت و قابل‌سازگاری است، نه تعریف نهایی هویت Thought.

### مفاهیم مستقل، نه خط لولهٔ اجباری

| مفهوم | قرارداد |
| --- | --- |
| **Material** | ورودی خام و قابل ثبت: یادداشت، متن چسبانده‌شده، فایل، پاسخ AI یا ثبت جلسه. ممکن است هیچ Thought نسازد یا چند Thought از آن فهمیده شود. |
| **Thought** | واحد قابل‌شناساییِ فکرِ هنوز حل‌نشده؛ می‌تواند مستقیماً نوشته شود یا از Material برخیزد. ممکن است هرگز به Knowledge نرسد. |
| **Knowledge** | ادعای ساخت‌یافته، تصمیم یا خط قرمزِ کاندیدِ ورود به Context. ساخت Knowledge از Material الزاماً از Thought عبور نمی‌کند. |
| **Truth** | Knowledge با وضعیت و اختیار تأییدشده طبق قواعد Mabda؛ Truth موجودیت یا پاسخ مدل جداگانه نیست. فرض—even اگر در UI تأیید شده باشد—همچنان با برچسب فرض نگه داشته می‌شود و واقعیت قطعی شمرده نمی‌شود. |
| **Output** | خروجی تولیدشده با Context مجاز؛ خودِ خروجی Truth نیست و نسخهٔ دقیق Context مصرف‌شده را در `usedContext` نگه می‌دارد. |

پس `Material ≠ Thought ≠ Knowledge ≠ Truth ≠ Output` مرز مفهومی را می‌گوید، نه مراحل اجباری. Proposed نوع Knowledge تازه‌ای نیست: Knowledge با وضعیت تأییدنشده است؛ فقط Confirmed تحت اختیار کاربر می‌تواند مبنای Truth باشد. هیچ Material یا Thought به‌طور ضمنی به AI عرضه نمی‌شود؛ کمک AI به Thought فقط در مسیر اختصاصی و پس از انتخاب صریح کاربر مجاز است و Thought در بلوک جداگانهٔ تأییدنشده می‌ماند.

### هویت، ویرایش و بازنگری

- **Thought باید هویت پایدار داشته باشد، اما نه یک موجودیت سنگین.** قرارداد هدف یک شناسهٔ پایدار و کمینه برای Thought است؛ متن، نوع، گره، ترتیب، موقعیت بوم و هش متن شناسه نیستند. معنای شناسه با عمل صریح کاربر حفظ می‌شود، نه با فاصلهٔ متنی.
- **ویرایش نمایشی:** اصلاح فاصله، نشانه‌گذاری، قالب یا بازنویسی هم‌معنا که ادعا/پرسش/مقصد حل‌نشده را عوض نمی‌کند؛ همان Thought و بدون Revision معنایی.
- **Revision معنایی:** همان مسئله یا ادعا ادامه دارد، اما مقدار، دامنه، شرط یا محتوای مهمش عوض می‌شود؛ همان شناسه، یک بازنگری ثبت‌شده. نمونه: «قیمت اشتراک ۴۰۰ باشد» ← «قیمت اشتراک ۴۹۰ باشد»: Revision همان پیشنهاد قیمت است، نه Thought تازه. هر تغییر تایپی Revision نیست.
- **Reclassification:** برچسب غلط اصلاح می‌شود اما معنای Thought دست‌نخورده است؛ همان شناسه و بدون Revision معنایی. نمونه: «آیا مشتری حاضر است پول بدهد؟» که اشتباهاً Idea خورده، با تغییر برچسب به Question همان Thought می‌ماند.
- **تغییر برچسب به‌تنهایی هویت را عوض نمی‌کند، اما هر تغییر نوع هم صرفاً Reclassification نیست.** «شاید قیمت را پایین بیاوریم» ← «آیا قیمت مانع خرید است؟» از پیشنهاد اقدام به پرسش تشخیصی رفته؛ قرارداد پیش‌فرض آن را Thought تازهٔ مشتق از قبلی می‌داند. اگر کاربر فقط برچسب را اشتباه زده باشد و معنای پرسش همان باشد، Reclassification است.
- **Derived Thought:** موضوع یا ادعای تازه‌ای که از Thought دیگری آمده است؛ شناسهٔ تازه می‌گیرد و پیوند `derived_from` دارد. جایگزینی متن قبلی نیست. اگر همان مسئلهٔ مرکزی ادامه دارد، Revision است؛ اگر واحد فکری مستقلی به‌وجود آمده، Derivation است.
- **Branch:** چند Thought مستقل و موازی از یک Thought/پرسش والد، معمولاً گزینه‌ها یا توضیح‌های رقیب؛ نوع موجودیت/رابطهٔ جدا نیست، چند فرزند `derived_from` است.
- **Synthesis:** Thought تازه‌ای که از چند Thought ورودی ساخته شده؛ به همهٔ ورودی‌ها `derived_from` دارد. اگر نتیجه خودش ادعای ساخت‌یافته است، مستقیم Knowledge پیشنهادی ساخته می‌شود؛ نیازی به Thought واسط نیست.
- **Split:** تجزیهٔ یک Thought به چند Thought مستقل؛ هر فرزند شناسهٔ تازه و `derived_from` والد دارد. والد خودکار حذف یا بسته نمی‌شود؛ تصمیم دربارهٔ بازماندن/حل‌شدنش با کاربر است.

مثال‌ها: «چرا conversion پایین است؟» با سه توضیح ممکن، یک پرسش والد و سه Thought مشتق/شاخه است؛ هیچ‌کدام Revision دیگری نیست. سه Thought مرتبط که به یک نتیجهٔ ترکیبی می‌رسند، یک Synthesis تازه می‌سازند؛ اگر نتیجه Knowledge است، همان نتیجه به‌صورت Proposed ثبت می‌شود. «Branch / Synthesis / Split» در این قرارداد واژگان مدل‌اند، نه قابلیت یا اصطلاح تازهٔ UI.

### چهار چیپ و Open Decision

- چیپ‌های فعلی **Idea، Question، Assumption، Open Decision** در P1 حفظ می‌شوند؛ این توافق دربارهٔ UI، ادعای هم‌محور بودن معناهایشان نیست.
- **Idea و Question** شکل/قصد Thought هستند: طرح یا پرسش حل‌نشده.
- **Assumption** موضع معرفتی دربارهٔ یک ادعاست، نه صرفاً شکل بیان. تبدیلش به Knowledge، Fact از نوع فرض و همیشه Proposed می‌سازد؛ تأیید معمول آن را خودبه‌خود به واقعیت تبدیل نمی‌کند.
- **Open Decision** یک مسئلهٔ تصمیم باز است که در UI همچنان با چیپ فعلی دیده می‌شود؛ در معنا، صرفاً هم‌نوع Idea نیست. قرارداد حداقلی آن: پرسش/مسئله، گزینه‌ها، دلیل یا شاهد اختیاری برای گزینه‌ها، و یک انتخاب/Resolution. گزینه و دلیل زیرساختِ استدلال تصمیم‌اند، نه Thoughtهای عمومی.
- گزینه‌های فعلی از خط‌های فهرست زیر همان خط تصمیم خوانده می‌شوند؛ `@«…»` برای گزینه می‌تواند شاهد/اتکای آن را نام ببرد. انتخاب، Decision پیشنهادی با `DecisionRecord` (گزینه‌های کنارگذاشته‌شده و دلیلشان) می‌سازد؛ Proposed هنوز Truth نیست و تأیید جداگانه می‌خواهد. ارزیابی سناریو، احتمال، امتیازدهی یا چارچوب تصمیم گسترده در این قرارداد نیست.

### حداقل روابط

### شکاف پیش از اجرا و مرز P1

تا پایان P1، `Note` در migration ۲ فقط `id/workspace/node/content/createdAt/updatedAt` داشت؛ Thought از نشانگر/علامت سؤال درجا مشتق می‌شد و شناسهٔ ذخیره‌شده نداشت. این توصیف تاریخچهٔ شکاف است، نه مدل فعلی.

در مقابل، Knowledge از قبل نسخه و Change مستقل (`context_objects.version`، `context_object_versions`، `context_changes`) داشت. مهاجرت P2 این شکاف‌ها را با کمترین مدل بست؛ جزئیات واقعی در «اجرای P2» آمده است.

### اجرای P2 — مدل ذخیره‌شده و رفتار واقعی

- Migration 21 به‌صورت forward-only جدول‌های `thoughts`، `thought_revisions` و `thought_derivations` را می‌سازد. هر Thought شناسهٔ مستقل، `workspaceId`، `nodeId`، نوع، متن، وضعیت و لنگر/نقل Note اختیاری دارد. Migration خودش parser/normalizer نسخه‌ثابت دارد؛ اجرای آن به رفتار parser آیندهٔ UI وابسته نیست.
- Backfill با ترتیب ثابت Note و رخدادهای خط، ID قطعی `legacy_thought_<noteId>_<ordinal>` می‌سازد؛ خطوط مشابه/تکراری جدا می‌مانند. Sourceهای Knowledge قبلی ابتدا با lineKey/hash، سپس متن نرمال‌شده و در پایان تطبیق نرمِ کمکی وصل می‌شوند تا وضعیت resolved و `resolvedObjectId` تا حد ممکن بماند. رسید قدیمی «ساخت بخش» resolved می‌ماند؛ اگر نوعش قابل‌اثبات نباشد `kind = null` است. متن Note و وضعیت/نسخهٔ Knowledge موجود دست‌نخورده می‌مانند؛ اجرای تکراری migration به‌علت versioning، Thought تکراری نمی‌سازد.
- Noteهای تازه و نشانگرهای Thought همچنان مسیر ورودی ساده‌اند. همگام‌سازیِ Note، لنگر را با `sourceLineKey` تطبیق می‌دهد و جابه‌جایی/قالب‌بندی را بدون تغییر هویت دنبال می‌کند؛ تغییر نوع نشانگر با متن ثابت، Reclassification همان ID است. حذف نشانگر یا تغییر متن خام Note، Thought قبلی را حذف یا بازنویسی نمی‌کند؛ خط نشان‌گذاری‌شدهٔ تازه ID تازه می‌سازد. برای تغییر متن همان Thought، کاربر از «بازنگری متن یا نوع» استفاده می‌کند.
- اقدام بازنگری متن همان ID را نگه می‌دارد. فقط وقتی `lineHash` نرمال‌شده عوض شود، یک رکورد `beforeText/afterText` افزوده می‌شود؛ فاصله/نشانه‌گذاری که hash را عوض نمی‌کند Revision نمی‌سازد. Reclassification از مسیر صریح همان ID را حفظ می‌کند و متن را در تاریخچه نمی‌برد. تشخیص با AI انجام نمی‌شود.
- Derivation یک ID تازه می‌سازد و فقط یال `derived_from` صریح ذخیره می‌کند؛ پشتیبانی داده‌ای چندوالدی موجود است. عملیات `deriveThought` (شاخه)، `synthesizeThoughts` (ترکیب چند والد به یک فکر) و `splitThought` (تفکیک یک فکر به چند فکر مشتق) در هسته و API پیاده‌سازی شده‌اند.
- Migration 23 جدول‌های `thought_about` (ارتباط پایدار فکر با دانش یا بخش، مستقل از متن و دست‌نخورده در ویرایش متنی) و `thought_events` (ثبت رویدادهای ایجاد، بازنگری، تغییر دسته‌بندی و حل فکر) را به‌صورت forward-only اضافه می‌کند. ارجاع‌های `@«...»` با عنوان‌های یکتا به‌طور قطعی backfill شده و عناوین مبهم هرگز حدس زده نمی‌شوند.
- تاریخچه و تبار فکر از طریق `getThoughtHistory` (شامل رویدادها، تغییر متن، فکرهای مشتق و پیوند به دانش پیشنهادی) استخراج شده و در رابط کاربری با دیالوگ مینیمال «دیدن تاریخچه» بدون اصطلاحات Git نمایش داده می‌شود.
- `ObjectSource.thoughtId` ارجاع promoted-to است و زنجیرهٔ Note/quote را حفظ می‌کند. هر مسیر ساخت Knowledge از Thought فقط Proposed می‌سازد و همان تراکنش Thought را resolved می‌کند؛ `updateObject` و جریان تأیید موجود همچنان تنها اختیار تبدیل Proposed به Truth هستند. Assumption فقط Factِ علامت‌خورده و Open Decision فقط Decision می‌شود؛ Idea/Question نیازمند انتخاب صریح نوع مقصد هستند.
- `thinkingSpace` و شمارنده‌های UI از رکوردهای Thought می‌خوانند. Note خام و Thought در AI/output به‌طور ضمنی تزریق نمی‌شوند. مسیر P3 کمک AI فقط IDهای Thought بازِ انتخاب‌شده را از سرور resolve می‌کند؛ Context آن مسیر فقط دانش Confirmed است، Thoughts در بخش صریح «تأییدنشده» می‌آیند و درخواست کاربر بعد از آن‌هاست. این مسیر در facts/Truth، output یا `usedContext` قرار نمی‌گیرد. مکانیسم آزاد/فضایی Canvas رابطه نمی‌سازد؛ Note آزاد و مختصاتش همان Material نمایشی‌اند.
- وضعیت حل‌شدن برای ساخت Node ذخیره می‌شود، اما چون P1 رابطهٔ Thought→Node را تأیید نکرد، مقصد Node جداگانه ثبت نمی‌شود. برای Thoughtهای resolved با `kind = null` نیز چیپ ساختگی نمایش داده نمی‌شود.

### ناورداها

1. Thought نه Material است، نه Knowledge و نه Truth؛ هیچ مسیر اجباری از یکی به بعدی وجود ندارد.
2. هیچ Thought یا Note خامی بدون درخواست صریح کاربر وارد AI نمی‌شود؛ Thought انتخاب‌شده هم فقط با برچسب تأییدنشده می‌آید. Thought هرگز Truth نیست؛ ترویج فقط Knowledge با وضعیت Proposed می‌سازد.
3. هویت Thought با شناسهٔ پایدار و تصمیم صریح دربارهٔ «ادامهٔ همان» یا «چیز تازه» تعیین می‌شود؛ متن، نوع، hash، گره، فاصله و جایگاه آن را تعیین نمی‌کنند.
4. تغییر برچسب به‌تنهایی هویت را عوض نمی‌کند؛ Revision معنایی همان هویت را حفظ می‌کند؛ Derivation هویت تازه دارد.
5. ساختار، بخش، قاب، موقعیت، ترتیب و drag فقط سازمان‌دهی/نمایش‌اند و رابطهٔ معنایی استنتاج نمی‌کنند.
6. هر Output، Lineage نسخه‌دار Context را حفظ می‌کند؛ تغییر Thought به‌تنهایی خروجی را قدیمی نمی‌کند تا وقتی Knowledge/Context مصرف‌شده تغییر نکرده است.
7. هر ویرایش Raw Note مستقل از Thought است؛ هیچ تطبیق متنی، هویت یا Revision معنایی را حدس نمی‌زند.
8. روابط معنایی پایدار Thought فقط با عملیات صریح ایجاد می‌شوند: `thought_derivations` برای تبار و `thought_about` برای زمینه. پیوند Thought به Knowledge از `ObjectSource.thoughtId` مشتق می‌شود. هیچ رابطه‌ای از متن، نزدیکی، قاب، ترتیب یا موقعیت بصری استنتاج نمی‌شود. ارجاع متنی `@«...»` فقط مسیر ورودی و سازگاری است و در صورت ابهام هرگز حدس زده نمی‌شود.

## درخت، ترتیب و تقدم

- **درخت = دامنه و ارث‌بری.** گره می‌گوید یک ادعا «دربارهٔ چه» است و زیرگره‌ها از والد ارث می‌برند. این‌که یک گره بالاتر یا چپ/راست‌تر از هم‌سطحش باشد فقط نمایش است (`order` برای چیدن است، نه معنا) و هیچ موتوری آن را نمی‌خواند.
- **تقدم فقط از `depends_on` می‌آید.** «این تصمیم روی آن سوار است» تنها یالی است که ترتیب می‌سازد (`decisionGraph`، لایه‌بندی نقشه). جایگزینی (`supersedes`) و تبار (`derived_from`) جریان زمان/ساخت‌اند، نه تقدمِ دامنه.
- **در نمای کلی حقیقت:** ردیف‌ها بخش‌اند و فقط یال `depends_on` جایگاه ستون را می‌سازد؛ عمق درخت با وابستگی یکی نیست. وقتی در داده‌های فعلی نما یالی نیست، عنوان «بدون وابستگی در این نما» می‌آید، نه «پایه». ردیف، قاب و جای کارت هیچ رابطه‌ای نمی‌سازند. «دور این مورد» همان نمای وابستگی/اثر را برای یک دانش کانونی می‌کند.

## تصمیم‌های باز

1. **کلید «این گره مستقل است».** امروز سازمان‌دهی (کجا قرارش بدهم؟) و ارث‌بری (چه چیزی را به ارث ببرد؟) یکی‌اند: برای این‌که یک ادعا از والد ارث نبرد باید آن را به گرهٔ دیگری ببری. پیشنهاد: کلیدی روی گره که ارث‌بری را قطع کند بی‌آن‌که جایش در درخت عوض شود. هنوز ساخته نشده؛ چون ارث‌بری در `contextEngine`، `aiContext` و بستهٔ Context خوانده می‌شود، هر سه باید با هم عوض شوند.
2. **سه محور به‌جای یک درخت.** *دامنه* (درخت: دربارهٔ چه)، *وابستگی* (`depends_on`: روی چه سوار است)، *بُعد* (برچسب‌های متقاطع مثل مخاطب/کانال/فصل که با دامنه یکی نیستند). امروز فقط دو محور اول مدل شده‌اند و «بُعد» با گره‌های تکراری یا slotKey دور زده می‌شود. هر محوری که اضافه شود باید قاعدهٔ بالا (فقط محور وابستگی تقدم می‌سازد) را نگه دارد و حتماً یک موتور بخواندش.
3. **سقف `customSpecs` (گزارش، نه تغییر).** امروز `customSpecs` یک بولی است: Starter ندارد، Pro و Max دارند. هزینهٔ یک جریان کار سفارشی برای ما تقریباً صفر است (یک JSON کوچک)؛ هزینهٔ واقعی ساخت خروجی با سهمیه و اقتصاد اجرای پلتفرم کنترل می‌شود. پس قفل فعلی **اهرم ارتقاست، نه محافظ هزینه**. ارزش دارد (جریان کار سفارشی ویژگی «قدرتی» است و کتابخانهٔ ۱۰تایی + قالب‌ها به Starter کار می‌دهد) ولی دو ایراد دارد: (الف) کاربر Starter نمی‌تواند حتی یک جریان کار خودش را امتحان کند و ارزشش را ببیند؛ (ب) «قالب جریان کار» را می‌شود ذخیره کرد ولی بازآوردنش قفل است. گزینهٔ پیشنهادی برای تصمیم اقتصادی: تبدیل به **تعداد** (مثلاً Starter ۱، Pro ۱۰، Max نامحدود) در `entitlements.config.ts`. تغییری داده نشد.
4. **چه چیزی را «تصمیم روی نمودار» می‌گذاریم.** امروز هر تصمیمی که یک بار Confirmed شده خط عمودی روی همهٔ نمودارها می‌گیرد، و فقط آن‌هایی که انتظار از همان شاخص دارند پررنگ و فهرست‌شده‌اند؛ بقیه کم‌رنگ و زیر «N تصمیم دیگر». اگر فضا شلوغ شد، فیلتر بر اساس بُعد/گره گزینهٔ بعدی است. تصمیمی با دو انتظار از دو شاخص هنوز ممکن نیست (یک `metricExpectation` برای هر تصمیم) — اگر لازم شد، آرایه می‌شود؛ ساختار داده (شاخص، مقدار، واحد، روز، ارجاع به تصمیم) آمادهٔ تحلیل بعدی است ولی هیچ مدلی ساخته نشده.

### چه چیزی ثابت است (قانون اساسی، در کد، هیچ قالبی عوض نمی‌کند)
Workspace مرز حقیقت؛ سه نوع دانش (واقعیت، تصمیم، قید)؛ وضعیت‌ها و اقتدار؛ انواع رابطه و قواعدشان (`depends_on` تنها منبع تقدم)؛ Proposed هرگز واقعیت نیست؛ یادداشت هرگز به AI نمی‌رود؛ نمونه‌ها (sample) به هیچ AI و موتوری نمی‌رسند؛ هر دانش جایی در درخت دارد.

### چه چیزی داده است
درخت گره‌ها، نام و توضیح‌شان، ترتیب‌شان؛ «شروع‌های آماده» (قالب‌های داده)؛ قالب گره؛ نمونه‌ها؛ «دانش لازم پیشنهادی». هیچ گره‌ای قفل نیست؛ همه قابل تغییر نام، جابه‌جایی و حذف‌اند.

### وضعیت اجرا
- **اجرا شد:** `is_system` بی‌اثر (migration ۱۸)؛ `defaultNodeId/resolveNodeId/treeOrder/defaultTransferTarget`؛ همهٔ `'business'`های سرور و کلاینت از درخت می‌آیند (یادداشت، استخراج، فایل، بلوک پاسخ AI، شروع سریع، بوم، دیالوگ‌ها؛ MCP در زمان این ممیزی وجود داشت و در P5 حذف شد)؛ `requiredContext.nodeId` فقط اشاره است؛ ترتیب Context از `nodeRank`؛ هدف تولید خروجی = کل Workspace؛ `NODE_ORDER`، `NODE_LABELS`، `NODE_IDS` و `KnowledgeGapChart` (بلااستفاده بود) حذف؛ `StartTemplate` واحد برای شروع آماده و قالب گره + `parseTemplate`؛ حذف امن (مقصد پیش‌فرض، فایل‌ها هم شمرده می‌شوند، `node_deleted`)؛ «بخش اصلی تازه» (ریشهٔ دوم)؛ شروع «خدمات» گره می‌آورد.
- **ماند (داده است، نه قانون):** `seedData.ts` و نمونهٔ قهوه گره‌ها را با همان شناسه‌های شروع پیش‌فرض می‌نویسند؛ ورود قدیمی (`importObject`) گرهٔ ناموجود را به جای پیش‌فرض می‌برد.
- **کشف حین کار:** حذف گرهٔ «فقط‌فایل‌دار» پیش‌تر فایل‌ها را بی‌گره می‌گذاشت (فایل‌ها شمرده نمی‌شدند)؛ رفع شد.

## فکر جدا از حقیقت، جابه‌جایی گره، پیش‌نویس روی تأییدشده

- **حقیقت = آخرین نسخهٔ تأییدشده.** متن ویرایش‌شدهٔ تأییدنشده در `context_objects.draft` (migration ۱۹) می‌ماند؛ ستون‌های `title/content/examples` فقط متن تأییدشده‌اند. AI، خروجی‌ها، Gap/Readiness/تناقض، `effectiveFor` فقط همان را می‌خوانند. تأیید پیش‌نویس = جایگزینی با نقطهٔ عطف نسخه؛ رد = دورریختن. هیچ انبار جدایی نیست.
- **نمایش جدا، داده یکی.** فضای فکر (`thinkingSpace`) = Thoughtهای بازِ ذخیره‌شده + Proposed + پیش‌نویس‌ها. نماهای حقیقت فقط دانش تأییدشده؛ فرضِ تأییدشده با نشان «فرض». در منبع حقیقت «ساختار» جای هر دانش را نشان می‌دهد و «نمای کلی» وابستگی‌های بین دانش‌ها را؛ در فکر، بوم آزاد برای گسترش فکر است.
- **مسیر ترویج فکر:** Thought ← انتخاب صریح نوع Knowledge ← Proposed ← تأیید کاربر. برای کمک AI مسیر جداگانه و صریح وجود دارد؛ Thought فقط به‌عنوان دادهٔ تأییدنشده می‌رود، نه Knowledge/Truth. هیچ Thought مستقماً Truth نمی‌شود.
- **جابه‌جایی گره:** هر گره به بخش اصلی/بالا/پایین/سطح/ترتیب می‌رود؛ اثرش (چه ارث‌بری قطع یا وصل می‌شود) پیش از تأیید گفته می‌شود (`moveEffect`)؛ `node_moved` Change با دلیل اختیاری. ترتیب فقط نمایش است و تقدم را عوض نمی‌کند.

## فکر و حقیقت در منو، رابطهٔ پیشنهادی، چرخه

- **چهار مقصد:** خانه · فکر · منبع حقیقت · خروجی‌ها. «فکر» مقصد جداست (فهرست + بوم)، نه نمایی از منبع؛ «خروجی‌ها» = ساخت (جریان‌های کار) + «خروجی‌های تو» (دارایی‌ها).
- **رابطهٔ پیشنهادی:** رابطهٔ `depends_on` با یک سر غیرتأییدشده (`Proposed`/`Needs Review`) حقیقت نیست: `needsReview` و خروجی Markdown آن را نمی‌بینند و در نمای کلی حقیقت (بدون «در راه است») نیست. با تأیید آن سر همان رابطهٔ واقعی می‌شود؛ جدول یا وضعیت تازه‌ای نیست.
- **فکر خام رابطهٔ نوع‌دار نمی‌سازد.** فقط «دربارهٔ این دانش» با `@` در متن؛ هنگام «به دانش ببر» به‌صورت **پیشنهاد** رابطه می‌آید.
- **تصحیح:** `depends_on` در Context **چرخه را منع نمی‌کند** (فقط خودوابستگی ممنوع است): `decisionGraph` اعضای یک چرخه را یک واحد «با هم تصمیم‌گرفتنی» می‌داند و نقشه چرخه را لایه‌بندی می‌کند. فقط گراف جریان‌های کار (`specGraph`) چرخه را می‌بندد. این‌جا قاعده‌ای اضافه نشد چون «دو تصمیمِ وابستهٔ دوطرفه» معنا دارد.
- **فکر ← بخش:** یک فکر می‌تواند یک گره (بخش) بشود، زیر هر والد یا در سطح اول؛ Thought resolved می‌شود و متن Note خام بدون تغییر می‌ماند.

## دامنهٔ بسته و درخواست برای AI (یک قاعده)

یک «بستهٔ دانش» و «درخواست برای AI» **یک** قاعدهٔ دامنه دارند (`src/core/packScope.ts`، `scopeSeeds` + `standingOver`). دامنه = چند بخش انتخاب‌شده + کلید «با زیربخش‌ها»؛ هیچ بخشی انتخاب نشود = کل درخت. دانشِ هر بخش از «فهرست مؤثر» (`effectiveFor`) خوانده می‌شود.

| چیز | بخش انتخاب‌شده | چرا |
| --- | --- | --- |
| دانش خود بخش | می‌آید | `own` |
| دانش بخش‌های بالاتر (والدها) | می‌آید | ارث‌بری رو به پایین |
| قید یا هر چیز «همه‌جا» (`reach: global`؛ پیش‌فرض قید) | می‌آید، از هر بخشی که نوشته شده، با برچسب «از "برند"، همه‌جا» | `global` |
| قید «فقط این بخش» | فقط اگر آن بخش (یا زیربخشش) در دامنه باشد | `reach: position` |
| زیربخش‌ها | **فقط با «با زیربخش‌ها»** (یا جدا تیک‌خورده)؛ بدونش در «چه نیامد» با دلیل «زیربخشی که انتخاب نشده» | مثل گفتگوی گره و شکاف‌های ممیزی که زیردرخت را می‌خوانند |
| بخش‌های هم‌سطح | هرگز | ارث نمی‌برند |
| کنار گذاشته (استثنا `overrides`) | در بخشی که کنار گذاشته شده نمی‌آید؛ در والدش می‌آید | `validOverrides` |
| منقضی | هرگز | `validUntil` گذشته |
| فرض | بسته: فقط با تیک، جدا و برچسب «واقعیت نیست»؛ درخواست: می‌آید جدا (به‌جز «سؤال») | بخش فرض و قاعده‌اش |
| پیشنهادی / نیازمند بررسی | بسته: فقط با تیک و برچسب «تأییدنشده»؛ درخواست: هرگز واقعیت نیست | `Proposed` هرگز واقعیت |
| نمونه (sample) و یادداشت | هرگز | نه دانش‌اند |

- **پیش‌فرض «با زیربخش‌ها»:** بستهٔ تازه و درخواست روشن؛ بستهٔ ذخیره‌شدهٔ پیش از این کلید خاموش می‌ماند (خروجی‌اش زیر پای کاربر عوض نشود). بستهٔ یک جریان کار بخش‌هایی را که نام می‌برد **با زیربخش‌هایشان** می‌خواند (همان که تولید می‌خواند). اثر بر بودجه: بسته بودجه ندارد (پیش‌نمایش «بلند است» می‌دهد)؛ درخواست بودجهٔ توکن دارد و مرتبط‌ترین‌ها می‌مانند.
- **بسته‌های نوع درخواست** همهٔ بخش‌های انتخاب‌شده را می‌خوانند (پیش‌تر فقط اولی).
- **گرهٔ ثابت نیست:** `requiredContext.nodeId` فقط اشاره است (`resolveNodeId`)؛ `seeds.push('content')` برداشته شد؛ `noFixedNodes.test.ts` منبع را برای شناسهٔ ثابت گره می‌پیماید.
- **شفافیت:** هر بسته/درخواست یک `Explain` (`scopeExplain.ts`) از **همان داده‌ای که متن را می‌سازد** می‌دهد: «آمد» (گروه‌بندی: قیدها، دانش تأییدشده، تصمیم‌ها، فرض‌ها، تأییدنشده‌ها + منشأ) و «نیامد» (دلیل جمله‌ای). قید را نمی‌شود از بسته برداشت؛ پیوند «ببین و ویرایش» به همان قید می‌رود که «محدودهٔ اثر» آن‌جا تعیین می‌شود.

## بایگانی، حذف و برگرداندن (قاعدهٔ ثابت؛ جدول در `docs/removal.md`)

- **سه واژه:** «بایگانی» (برمی‌گردد؛ تاریخچه می‌ماند)، «حذف» (کار کوچک و دورریختنی؛ با «برگرداندن»)، «حذف دائمی» (برنمی‌گردد؛ همیشه دو مرحله).
- **دانش** هرگز مستقیم پاک نمی‌شود: اول «بایگانی» (`status = Archived`، نسخه‌ها و منشأ سالم، «برگردان» با وضعیت قبلی). **حذف دائمی فقط از بایگانی یا جایگزین‌شده** (سرور دیگر را رد می‌کند) و متن را از **هر جدولی** می‌برد: ردیف، نسخه‌ها، `context_changes` (before/after/reason)، پیش‌نویس، رابطه‌ها، جای بوم، قضاوت‌ها، نام در بستهٔ ثبت‌شده و اشارهٔ خروجی‌ها. می‌ماند: یک Change بی‌محتوا (`purged`). خروجی‌های ساخته‌شده متن خودشان را نگه می‌دارند و `removedSources` می‌گیرند (نه «قدیمی»).
- **گره** با `nodeRemovalPlan` برنامه‌ریزی می‌شود: «انتقال» (والد پیش‌فرض) یا «بایگانی شاخه» (دانش‌ها بایگانی؛ یادداشت/فایل‌ها به مقصد). هر دو یک دستهٔ `removal_batches` می‌سازند که `undoRemoval` دقیق برمی‌گرداند (گره‌ها، ترتیب، جابه‌جایی‌ها، وضعیت‌ها). مقصد را API صریح می‌خواهد.
- **خروجی:** `archivedAt` روی دادهٔ خودش (ذخیرهٔ مجدد آن را لغو نمی‌کند)؛ بایگانی‌شده در هیچ فهرست و شماری نیست. **Workspace:** `archivedAt` فقط سمت سرور. حذف Workspace و «همهٔ داده‌ها» **از روی schema** هر جدولی را که `workspace_id` / `user_id` دارد خالی می‌کنند.
- **صداقت:** هیچ دکمه یا پیامی نمی‌گوید کاری انجام شد جز آنکه واقعاً شده؛ «حساب» به‌عنوان مفهوم نیست (یک کاربر محلی).

## منطق ساده‌سازی وابستگی (جمع‌بندی)
هیچ‌کدام از این واژه‌ها به کاربر نمی‌رسد؛ کاربر فقط جمله‌های ساده می‌بیند.
- **لینک اضافه** (`src/core/dependencyReduction.ts`): اگر A→B→C و A→C هم هست، لینک مستقیم کاری نمی‌کند؛ در جزئیات می‌گوییم «لازم نیست؛ از راه B به آن می‌رسد» با دکمهٔ «برش دار». چیزی خودکار حذف نمی‌شود. چرخه دست‌نخورده می‌ماند (هشدار خودش را دارد).
- **اثر غیرمستقیم** (`indirectReach`): بالادست و پایین‌دست چندقدمی محاسبه می‌شود و از کاربر پرسیده نمی‌شود.
- **تناقض فقط بین موارد هم‌زمان حاکم** (`coGoverning` در `contradictionCandidates.ts`): همان بخش، بخش و والدش، یا مورد «همه‌جا». دو بخش هم‌سطح که هیچ‌جا هم‌زمان حاکم نیستند هشدار نمی‌دهند، مگر کسی صریحاً به هم وصلشان کرده باشد.
- ارث‌بری و هم‌بخش بودن وابستگی نیستند و `needsReview` نمی‌سازند؛ `depends_on` تنها منبع تقدم است. خودوابستگی (self-dependency) ممنوع است، اما چرخه (cycle) میان تصمیم‌های Context مجاز است و به معنای «با هم تصمیم گرفته شوند» تلقی می‌شود؛ چرخه فقط در `specGraph` و خروجی‌های Workstream ممنوع است.
- **«کجا اعمال شود»** (`scopeMove.ts`): جابه‌جایی خانهٔ یک دانش و پیش‌نمایش اثر؛ مثل `nodeMove` پیش از تأیید می‌گوید کدام بخش‌ها می‌گیرند یا از دست می‌دهند.

## ساختار سرنخ است، نه حکم

> کاربر پرسید آیا درخت باید خودش رابطه بسازد. **نه.** ولی شهودش درست است: ساختار می‌تواند سرنخ بدهد. فرق «حکم» و «سرنخ» همین‌جاست.

**از درخت فقط یک چیز حکم است: ارث‌بری** (`effectiveFor`). چه چیزی در یک بخش حاکم است از درخت می‌آید و بس. هیچ رابطه، وضعیت یا `needsReview` از درخت ساخته نمی‌شود.

| قاعده | چرا |
| --- | --- |
| ارث‌بری ≠ وابستگی؛ هم‌بخش ≠ وابسته | جای بخش برای پیدا کردن است؛ جابه‌جایی نباید منطق را عوض کند (آزمون: `moveNode` هیچ رابطه‌ای نمی‌سازد و پاک نمی‌کند) |
| `needsReview` فقط از `depends_on` | n×m هشدار هشدارهای درست را می‌پوشاند |
| هم‌زمانی فقط با وابستگی دوطرفه | هم‌بخش بودن هم‌زمانی نیست؛ «تصمیم هم‌زمان به انتخاب کاربر» = «بستهٔ تغییر» در `docs/later.md` |
| رابطه ادعای گفته‌شده است | ادعای ساختگی اعتماد را می‌برد |

**سه سرنخ** (هر سه: قطعی، بدون AI، با دلیل جمله‌ای، بی‌اثر روی داده؛ تست‌ها همین را اجبار می‌کنند):

1. **خبر نرم ارث‌بری** (`src/core/inheritNotice.ts`): تغییر تأییدشدهٔ دانشی که در زیربخش‌ها هم حاکم است («این تغییر در N زیربخش هم حاکم است؛ اگر خواستی نگاهی بینداز»). شمرده نمی‌شود: زیربخشی که با `overrides` کنار گذاشته، دانش منقضی، پیش‌نویس/پیشنهادی و بخش بدون زیربخش. تغییرهای نزدیک (۶ ساعت، یک بخش) یک خبرند. نه `needsReview`، نه وضعیت، نه در شمارندهٔ «همه (N)». «دیدم» روی همین دستگاه ذخیره می‌شود.
2. **ترتیب پیشنهادی** (`src/core/decisionOrder.ts`): تصمیم یا خط قرمزِ بخش بالا پیش از مال زیربخش، با یک خط دلیل. فقط **حالت‌های مساوی** را می‌شکند (هم‌لایه در `decisionGraph`)؛ اگر بالادستی به پایین‌دستی وابسته باشد `depends_on` برنده است و دلیلی نشان داده نمی‌شود. قفل یا مانع نیست.
3. **پیشنهاد رابطه از بالادست** (`src/core/upstreamLinks.ts`): موقع نوشتن تصمیم/خط قرمز در زیربخش، تصمیم‌ها و خط قرمزهای تأییدشده‌ای که به اینجا می‌رسند و در عنوان دست‌کم یک واژهٔ مشترک دارند (حداکثر ۳، با «از بخش X به اینجا می‌رسد و از "قیمت" حرف می‌زند»). یک لمس می‌پذیرد، «نه» به خاطر سپرده می‌شود؛ چرخه ساخته نمی‌شود.

**هم‌پوشانی موضوع:** قاعدهٔ قدیم `mentions.ts` (دو واژهٔ مشترک و Jaccard ≥ ۰٫۴) برای دو دانش بی‌ارتباط می‌ماند. فقط جایی که ساختار خودش می‌گوید این دو نزدیک‌اند (دانشِ بالا که به زیربخش می‌رسد) یک واژهٔ مشترک بس است (`sharedTopic(..., { loose: true })`)؛ چون عنوان زیربخش معمولاً موضوع را باریک‌تر می‌نویسد («قیمت اشتراک» / «قیمت بستهٔ هدیه»).

## قرارداد P3 — تجربهٔ فکر و حلقهٔ فکر ↔ حقیقت

- **ثبت:** `ThoughtDialog` خط‌های بی‌تورفتگی را فکرهای پشت‌سرهم و خط‌های تو‌رفته را ادامهٔ همان فکر می‌گیرد. دکمهٔ «خط تازه در همین فکر» مسیر لمسیِ چندخطی است؛ Shift+Enter تنها راه نیست. متن و نوع را می‌توان پیش از ثبت اصلاح کرد و Thought ذخیره‌شده را از مسیر «بازنگری» اصلاح/بازطبقه‌بندی کرد.
- **Material در رابط:** یادداشت آزادِ گره و یادداشت آزادِ بوم برای متن خام‌اند؛ خودکار Thought نمی‌شوند و به AI تزریق نمی‌شوند. استخراج یادداشت از گره فقط با اقدام صریح است. برای فکرِ اقدام‌پذیر از «فکر تازه»/فهرست فکرها استفاده می‌شود. یادداشت بوم و مختصاتش رابطهٔ معنایی نمی‌سازد.
- **Truth ↔ Thought:** از جزئیات Truth تأییدشده «دربارهٔ این فکر کن» همان ThoughtDialog را با Question و `@«عنوان»` پیش‌گزیده باز می‌کند. Truth تغییر یا کپی نمی‌شود. Thinking Space در scope بخش، دانش Confirmed مؤثرِ همان بخش و زیربخش‌ها را به‌صورت anchor خواندنی نشان می‌دهد؛ کلیک همان Object را باز می‌کند. نمایش به ۸ anchor نخست محدود است.
- **فکر دربارهٔ بخش:** اقدام ساختار «روی این بخش فکر کن» فقط به Thinking Space با scope همان بخش می‌رود؛ مفهوم بستهٔ ذخیره‌شده یا snapshot جدیدی ساخته نمی‌شود. Thoughtهای باز در همان scope/ارجاع‌های صریح `about` دیده می‌شوند.
- **چندانتخاب و ترکیب:** انتخاب چندگانه فقط پس از درخواست کاربر فعال است. ترکیب، یک Thought با ID تازه و متن صریح کاربر می‌سازد و IDهای همهٔ والدهای انتخاب‌شده را با `derived_from` ثبت می‌کند. والدها دست‌نخورده می‌مانند؛ ترکیب نوع Thought جدا یا استنتاج از چیدمان نیست.
- **کمک AI به Thought:** فقط از اقدام صریح Thoughtهای انتخاب‌شده (حداکثر ۱۲) انجام می‌شود. سرور IDها را در فضای کار resolve و بازبودنشان را بررسی می‌کند؛ متن آزاد از مرورگر منبع Thought نیست. پیش‌فرض، دانش Confirmed مؤثر در بخش‌های همان Thoughtهاست؛ کاربر می‌تواند صریحاً کل کسب‌وکار یا یک بخش دیگر را برگزیند. انتخاب چند بخش به کل کسب‌وکار گسترش پنهانی ندارد. فایل، Note خام، Proposed و Needs Review بی‌درخواست اضافه نمی‌شوند. Thoughtها در بلوک مجزای «تأییدنشده؛ حقیقت نیستند» بعد از Context می‌آیند؛ قواعد قبل از درخواست کاربر و قالب پاسخ بعد از آن است. «کپی برای AI خودم» و «همین‌جا جواب بده» هر دو همین مرز را دارند.
- پاسخ AI یا با اقدام صریح کاربر به Thought مشتق‌شده از والدهای انتخاب‌شده تبدیل می‌شود، یا یک بلوک به‌عنوان Knowledge پیشنهادی باز می‌شود. هیچ مسیر مستقیمی از پاسخ/Thought به Confirmed وجود ندارد. تأیید Truth همان اختیار جاری کاربر است.
- **Progressive disclosure:** اقدام‌های معمول هر Thought همان ویرایش/طبقه‌بندی، ترویج Proposed و «بیشتر» برای مشتق‌سازی‌اند؛ انتخاب چندگانه فقط toolbar زمینه‌ای را نشان می‌دهد. در موبایل همان toolbar در جریان صفحه wrap می‌شود؛ bottom-sheet یا toolbar چسبانِ همیشه‌روشن اضافه نشده است.

**عمداً ساخته نمی‌شود:** پیش‌نمایش پیامد Option با Diff/اثر؛ Branch/Split به‌عنوان قابلیت مستقل؛ رابطه از مکان/قاب/نزدیکی/ترتیب؛ بستهٔ ذخیره‌شدهٔ «فکر این بخش»؛ و AI خودکار روی همهٔ Thoughtها.

## قرارداد P4 — نماهای حقیقت و جابه‌جایی ساختار

- **ساختار** جواب «چه چیزی کجاست؟» را می‌دهد: parent/child یعنی دامنه و ارث‌بری، نه dependency یا تقدم. عمق از زنجیرهٔ `parentId` مشتق می‌شود؛ فیلد معنایی جداگانه‌ای برای level نداریم.
- **نمای کلی** جواب «کل سیستم چگونه به هم وصل است؟» را می‌دهد: ردیف‌ها Nodeهای ساختاری و یال‌ها فقط رابطه‌های صریح `depends_on` هستند. ستون‌ها جایگاه گراف وابستگی را خلاصه می‌کنند؛ اگر در موارد فعلیِ نما یالی نیست «بدون وابستگی در این نما» نمایش می‌دهیم. «دور این مورد» نمای زمینه‌ای همان گراف است، نه مقصد یا چیدمان هم‌ارز دیگری؛ منشأ و خروجی‌های وابسته از دادهٔ lineage موجود می‌آیند.
- **سند** برای خواندن پیوسته و **جدول** برای مرتب‌سازی داده حفظ می‌شوند، اما در «نماهای بیشتر» هستند: این دو کار متفاوت‌اند و گزینهٔ layout دیگری برای دیدن یک چیز نیستند.
- **حرکت Node:** حرکت معمول، خود Node و همهٔ زیرشاخه‌اش را با هم می‌برد. اشیای دانش، Note، Thought، فایل و relationها با شناسهٔ خود می‌مانند؛ فقط والد Node عوض می‌شود. هیچ dependency از ساختار ساخته یا حذف نمی‌شود.
- پیش‌نمایش با همان تابع خالص ساخت درخت مقصد که commit استفاده می‌کند، `effectiveFor` را پیش/پس از حرکت برای تمام زیرشاخه مقایسه می‌کند. فقط Truth تأییدشدهٔ بیرون از زیرشاخه که از دست می‌رود/به‌دست می‌آید و تغییر اعتبار `overrides` گزارش می‌شود.
- **اثرهای محدود:** جابه‌جایی به‌تنهایی relation `depends_on` یا `needsReview` را تغییر نمی‌دهد و موتور فعلی Asset را به‌خاطر `node_moved` stale نمی‌کند. دامنهٔ مؤثر برای تولید بعدی ممکن است فرق کند، اما معماری فعلی lineage تولید را به محل هدف گره متصل نکرده است؛ این را اثر قطعی خروجی نمی‌نامیم.
- **عمداً ساخته نمی‌شود:** انتقال فقط والد، dependency خودکار از containment، نمای ساختاری/نقشهٔ ذهنی دوم، Change Set چندحرکتی، یا بازطراحی عمومی Canvas. نیاز به Change Set تا زمانی که کار یک انتقال واحد با پیش‌نمایش deterministic است، اثبات نشده و parked می‌ماند.

## وضعیت قابلیت‌های هوش مصنوعی و یکپارچه‌سازی پس از P5

- **پیاده‌سازی فعلی (Current Implementation):** مسیر اجرای هوش مصنوعی داخلی تنها با پیکربندی مدیریت‌شدهٔ پلتفرم پیاده‌سازی شده است و کاربر هیچ کلید، ارائه‌دهنده (Provider)، مدل یا اعتبارسنجی مستقیمی انتخاب نمی‌کند. بسته‌های Context، کپی/چسباندن و واردکردن عمومی پاسخ باقی می‌مانند؛ هرگونه محتوای بیرونی یا پیشنهادی تا زمان تأیید صریح کاربر همواره `Proposed` است.
- **تصمیم باز محصولی (Open Product Decision):** باقی ماندن هوش مصنوعی داخلی در محصول، دامنه و نقش آن (مشورتی/تحلیلی)، قابلیت‌های چندوجهی (Multimodal)، و جایگاه آن در پلن‌ها و مدل درآمدزایی (Monetization) هنوز قطعی نشده و یک تصمیم باز محصولی است. تا زمان تصمیم‌گیری، هیچ زیرساخت تازهٔ AI ساخته نمی‌شود و قابلیت فعلی نیز در این مرحله حذف نمی‌شود.
- **استقلال معماری هسته:** قابلیت‌های اصلی سیستم شامل Thought، About، Promotion، Truth، Provenance و Impact نباید و هیچ‌گونه وابستگی بنیادی به هوش مصنوعی داخلی ندارند و مستقل از مدل کار می‌کنند.
- **حذف‌شده از MVP:** سرور/توکن MCP، مدیریت اتصال، BYOK vault و مسیرهای ثبت کلید توسط کاربر، انتخاب provider/model و حسابداری هزینهٔ شخصی قطعی و حذف‌شده از MVP باقی می‌مانند. زیرساخت بلااستفاده برای «بعداً» نگه داشته نمی‌شود.
- **سازگاری تاریخی:** منبع/actor قدیمی `mcp` و marker قدیمی `LedgerEntry.byok` صرفاً برای تفسیر صحیح رکوردهای ذخیره‌شدهٔ قبلی خوانده می‌شوند؛ tokenهای فعال در migration v22 باطل شده‌اند اما رکوردهای تاریخی‌شان حفظ می‌شود. فایل‌های vault قدیمی هنگام شروع سرور پاک‌سازی می‌شوند و این سازگاری هیچ ورودی یا قابلیت فعالی ایجاد نمی‌کند.
